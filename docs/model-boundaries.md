# 水収支モデルの式と境界

## 基本式

日ごとのIT電力量:

```text
IT電力量[kWh/日] = IT負荷[MW] × 1000 × 24 × 稼働率
```

施設の直接水需要:

```text
直接水需要[L/日] = IT電力量[kWh/日] × WUE[L/kWh]
```

水源別の必要量:

```text
上水必要量 = 直接水需要 × 上水使用率
再生水必要量 = 直接水需要 × 再生水使用率
上水使用率 + 再生水使用率 = 1
```

ここで得る上水必要量は、施設が必要とする水量です。貯水池から実際に出た上水取水量は、供給政策と利用可能量を適用した別の値です。

## 施設内の水の行き先

実際に供給された上水と再生水を、次の排他的な区分へ配分します。

```text
供給水量 = 蒸発 + ブローダウン + 地域水系への返流水 + 回収可能排水
```

各施設の4比率は合計1でなければ設定エラーです。MVPの`potable_consumptive_use`は、供給上水のうち蒸発へ配分された部分です。ブローダウンを水質上すぐ利用できるとは仮定せず、消費と同一視もしません。

## 上水貯水池の保存則

```text
期首貯水 + 水源補給 + 増設配水池の供用時初期充水
= 溢水 + 住民供給 + データセンター上水取水 + 期末貯水
```

すべての日について誤差を`water_balance_error_l`へ記録します。貯水は0以上、容量以下に制限されます。住民不足と施設不足は非負です。

印西プロファイルの`storage_capacity_l = 48,000,000`は、千葉県営水道の令和6年度事業年報にある北総浄水場配水池の有効容量48,000 m³を容量代理値へ換算したものです。北総浄水場は千葉ニュータウン以外にも給水するため、48 MLは印西市専用の在庫ではありません。また、`initial_storage_l = 48,000,000`として満水開始させることは反実仮想の初期条件であり、2026年6月1日の実測貯留量ではありません。公表された物理容量と、モデル境界への転用・満水開始という仮定を分けて解釈します。

時間刻みは1日で、水源補給と供用時初期充水を日初の一括流入として扱います。期首貯水へ一括流入を加えた直後に容量を適用し、超過分を`spill_l`へ記録してから、その日の住民・データセンター需要を配分します。したがって、満水状態へ入った同日流入は、後続する同日需要で空きが生じても溢水として扱われます。日内の時刻別流入、需要との同時性、ピーク流量は表現しません。

この日内順序は結果に影響するモデル仮定です。夏季102日版の提出値は日初一括流入の順序で統一しています。旧365日版で行った代替順序の感度値は期間と物理条件が異なるため夏季結果へ流用しません。夏季版で別順序を比較する場合は、同じ2026年6月1日〜9月10日設定から再計算します。

再生水は上水貯水池の外側から来るものとして扱います。地域返流水と回収可能排水も記録だけを行い、同日の上水貯水池には戻しません。そのため、モデル全体は「水道事業体の上水貯水池」を中心とした境界であり、流域全体の循環モデルではありません。

配水池増設は供用日以降の容量を増やします。空の配水池を増設しても水源量は増えません。供用時の初期充水を設定した場合は、既存水量と混同せず外部流入として記録します。

## 任意の広域水源層と地域配水の分離

エンジンは、上記の地域配水バッファとは別に広域水源の基準層を持てます。広域水源を有効にする場合は次の収支を使います。

```text
広域水源期末
= 広域水源期首
  + 観測基準に含まれる日次純変化
  - シミュレーションで追加したDC上水消費
  - 広域水源溢水
  + 広域水源不足補正
```

観測貯水量を基準に使う場合、その値には既存の住民・産業・農業需要と自然流入、ダム運用がすでに反映されています。このため、既存住民需要を広域水源からもう一度差し引きません。DCの追加影響には上水「取水量」ではなく、蒸発として即時利用不能になった`datacenter_potable_consumptive_use_l`を用います。

夏季102日版では`regional_source`を無効にし、利根川上流ダム群を水収支の貯留層や配分元にはしていません。別の`observed_context`として、2025年6月1日〜9月10日の我孫子日降水量と、2025年6月1日〜9月11日の利根川上流9ダム10日値を読み込みます。2026年9月10日は成果物作成時点より後なので、2025年系列を2026年の同じ月日へ対応させる表示であり、2026年実績や予報ではありません。

観測コンテキストは`observed_precipitation_mm`、`observed_reservoir_reference_storage_l`などへ記録しますが、`source_inflow_l`、地域配水バッファ、住民・DCへの配分、制限発動条件を変更しません。我孫子の102日間の降水合計は394.5 mmですが、集水面積、流出率、取水可能率、浄水歩留まり、時間遅れを取得していないため、リットルへ換算しません。9ダム観測日の間の線形補間も表示用であり、補間値は観測値ではありません。

`observed_reservoir_counterfactual_with_dc_l`は、表示上の9ダム参照値から仮想DCの累積上水消費を差し引く診断オーバーレイです。北総浄水場や印西市に実際に割り当てられた量を表さず、地域水収支へ戻りません。北総系の水源施設には利根川河口堰、川治ダム、湯西川ダム、奈良俣ダムが関係しますが、利根川上流9ダム系列に含まれるのはこのうち奈良俣ダムだけです。9ダム系列を北総系統全体または印西専用水源と解釈しません。

地域配水側の`calibrated_service`モードでは次を使用します。

```text
基準供給量 = 当日の地域基準需要 × (1 + 明示した供給余裕率)
当日供給量 = 基準供給量 × 合成供給シナリオ倍率
```

夏季版の基準供給量は、県営水道全体の一人一日平均給水量を需要参照にし、合成した月別需要形状と10.5%の供給余裕を適用した値です。印西専用の観測供給量ではありません。同じ合成基準供給からDC需要だけを追加し、地域配水バッファの低下、DC制限、住民不足を政策別に比較します。2025年降水量と9ダム値はこの供給式へ入力せず、通常条件と渇水時93%倍率も2025年または2026年の天候再現・予報ではありません。

## データセンター敷地内水槽

```text
DC水槽期首 + 水道からの補給 = 施設への放出 + DC水槽期末
```

施設は水槽の水を先に直接需要へ使用し、その後、水道から不足分と設定済み補給上限までの再充水を要求します。水道から水槽へ入っただけの水は、その日の蒸発・ブローダウン・返流水には数えません。施設プロセスへ実際に送られた時点で水用途へ配分します。

## 供給政策

- `resident_first`: 利用可能な上水を住民へ先に割り当て、残量を施設へ供給
- `proportional`: 住民需要と許可済み施設需要の比率で利用可能量を配分

自治体エージェントが`enact_dc_restriction`を選んでも、当日の住民不足が正、または期末貯水率が設定済み発動閾値未満の場合にだけ、設定済み倍率を翌日の施設上水要求へ適用します。`lift_dc_restriction`は、制限中かつ期末貯水率が解除閾値以上の場合にだけ適用します。LLMが閾値外の政策変更を提案してもPython側で無効化します。倍率と閾値はPython設定で固定され、LLM出力中の数値は読み取りません。

## 反実仮想

```text
追加住民不足量
= データセンターありの累積住民不足量
  - 同じ合成基準供給／合成渇水ストレス条件でのデータセンターなし累積住民不足量
```

人口・初期貯水・合成供給条件・期間を揃え、データセンター条件だけを変更します。降水量や気象再現はこの比較へ含めません。
